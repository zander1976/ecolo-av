# Two lines, not one: the corridor

Ben, 26 Nov: "maybe instead of a line we use two lines and the car just needs to stay
between them."

| | |
|---|---|
| State | **Proposed** (26 Nov). Tonight's test: the tube made wider (below) |
| Where | `mpc_lag_rs` first (`aav_mpc_lag`); MPPI already prices lanes in the costmap |
| Scored by | `tools/lane_score.py` (in the lane, over a line, past the kerb) and the league's sway |

## 1. Today: one line, and a thin tube

```text
   left line ─────────────────────────────────────
                     ·  ·  ·  tube ±0.3 m
   the plan   ═══════════════════════════════════   ← the car is pulled to this
                     ·  ·  ·
   right line ────────────────────────────────────
```

- The planner draws **one line** (`/plan`); the followers are scored on how far they wander
  from it.
- `mpc_lag_rs` already has a **tube** (Ben, 21 Nov): no cost on the sideways error within
  ±0.3 m. It cut University Drive's sway from 0.251 to 0.160.
- The tube is the same width on both sides, and the same on a 3 m lane as on a 6 m one.

## 2. The idea: the lane's own edges are the tube

```text
   left line ─────────────────────────────────────
              ↑ left room (to the line, less half the car, less a margin)
   the plan   ═══════════════════════════════════   ← free anywhere in between
              ↓ right room
   right line ────────────────────────────────────
```

| Today | The corridor |
|---|---|
| target: e_y clipped to ±tube | target: e_y clipped to **[−right room, +left room]**, per point of the horizon |
| one width for every road | the room from the lane map (or the camera's lines, `/perception/lane/geometry`) |
| centred on the plan | can be lopsided: hug the right line on a two-way road |
| scored: off the path | scored: **stayed between the lines**, and how close to an edge |

It is the tube's clip with two numbers instead of one, so the solver does not change.

**Room** at a point = distance from the plan to that side's line − half the car's width
(`vehicle.yaml`) − a margin (start: 0.2 m). If the room is below 0 (a narrow lane), it is 0:
the car keeps to the plan there, as with no tube.

## 3. Where the two lines come from

| Source | When | Already there |
|---|---|---|
| the lane map (`maps/<area>/lanes.yaml`, `aav_description lane_map`) | mapped roads | yes: `lane_score.py` and the costmap's lanes layer read it |
| the camera's lines (`/perception/lane/geometry`) | where there is no map | yes: `camera_lanes.rs` draws them in the costmap |
| neither | a parking lot | the old ±tube |

## 4. What MPPI does

MPPI already follows the **costmap's lanes** (TODO 264): the right lane's centre costs
little, the yellow line more, the kerb most. That is a corridor with soft edges. The MPC
version above is the hard-edged twin, so the two can be scored on the same roads.

## 5. How we test it

| Step | Run | Pass mark (set before) |
|---|---|---|
| 1 (26 Nov) | `measure controllers --trackers mpc_lag_rs` on `university` with `mpc_lag_tube:=0.3`, `0.8`, `1.2`, 2 runs; `lane_score.py` on each | wider tube: less sway, **still 100 % in the lane**, never past the kerb |
| 2 | build the two-sided tube from the lane map | the same roads: in the lane 100 %, sway no worse than step 1's best |
| 3 | against MPPI's lanes on the same roads | a table; a worse score is fine if it opens room (Ben, 19 Nov) |

## 6. Ideas we learn from

- Apollo's and Autoware's path optimizers bound the sideways offset by the drivable area's
  edges, point by point, instead of tracking one line. To credit in
  `docs/acknowledgements.md` when we build step 2.
- Tube MPC in the literature keeps the state inside a set around a plan; ours is the
  simpler cost-free band.
